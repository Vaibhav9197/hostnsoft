# Capabilities

Everything Embarko can do, one entry each, in the order an agent needs it.
Every entry answers the same five questions: **what** it is, **why** it
exists, **when** to use it, **how** to use it, and its **limitations**.

**If this page and the live endpoint disagree, believe the endpoint.**
[`GET https://ship.embarko.ai/capabilities`](https://ship.embarko.ai/capabilities)
is generated by the platform itself, so it is always current. This page is
written by hand and can fall behind. It needs no token, is cached for an
hour, and is safe to read before you have a token — so call it before
relying on a feature. Each entry carries a `via` field naming who can
invoke it:

```json
{
  "runtime": { "port_env": "PORT", "bind_address": "0.0.0.0", "dockerfile": "rejected" },
  "persistence": { "data_dir_env": "DATA_DIR", "survives_redeploy": true, "survives_node_loss": false },
  "features": {
    "deploy":         { "status": "available", "via": ["agent", "dashboard"] },
    "env_vars":       { "status": "available", "via": ["agent", "dashboard"] },
    "rollback":       { "status": "available", "via": ["agent", "dashboard"] },
    "custom_domains": { "status": "available", "via": ["agent", "dashboard"] },
    "analytics":      { "status": "available", "via": ["agent", "dashboard"] },
    "rename_app":     { "status": "available", "via": ["agent", "dashboard"] },
    "change_app_address": { "status": "available", "via": ["agent", "dashboard"] },
    "delete_app":     { "status": "available", "via": ["agent", "dashboard"] },
    "backups":        { "status": "unavailable" }
  }
}
```

Entries marked **NOT AVAILABLE YET** are planned but absent. Planned is not
present: an app that needs one today cannot use it. Each says what to do
instead.

Almost everything here is agent-callable with a deploy token, including
custom domains, analytics, renaming and deletion. **One step is not:**
creating the DNS record for a custom domain, which only the domain's owner
can do at their own registrar.

Everything is on `ship.embarko.ai`, under two path shapes — and **the path
does not tell you the auth rule**:

| Auth | Calls |
| --- | --- |
| None, ever | `GET /capabilities`, `POST /api/public/…` (rate limited) |
| None while unclaimed, token once claimed | deploy, status, logs, agent feedback |
| **Deploy token, always** | domains, analytics, rename, change web address, delete, env vars, deployment history, rollback, showcase |

Deploy, status, logs, domains, analytics, rename and delete sit under
`/apps/<name>`; env vars, history, rollback and showcase sit under
`/api/apps/<name>`. Copy each path from its own entry rather than inferring
one.

## [Deploy application](#deploy)

**What:** Upload an app's source and get it built, running and served at a
live HTTPS URL.

**Why:** This is the platform's core action. Everything else exists to
support or adjust it.

**When:** The user asks to deploy, ship, publish, release or "put online" an
app you have built.

**How:**

```bash
tar -czf /tmp/app.tar.gz --exclude=node_modules --exclude=.git \
  --exclude='.env*' -C /path/to/app .

curl -X POST "https://ship.embarko.ai/apps" \
  -H "X-App-Name: my-app" \
  -H "X-App-Version: $(git rev-parse --short HEAD)" \
  -H "X-App-Type: portfolio" \
  -H "X-Agent-Name: claude" \
  -F "source=@/tmp/app.tar.gz"
```

No `Authorization` header is needed for a first deploy. `X-App-Type` is
optional. It says what the app is for (`personal website`, `portfolio`,
`task management`, `feedback system`...). Set it if you know. If you don't,
ask the user once. If they skip it, leave it out. `X-Agent-Name` is your own
name as an agent (`claude-code`, `claude`, `chatgpt`...). Always send it. Full parameter and
error reference: [API contract](api.md#deploy).

**Limitations:** Answers `202` — accepted, not live. Poll `links.status`
until `status` is `live` before reporting anything, and follow the `next`
field each reply carries. One deploy is one
app. The manifest or `index.html` must be at the archive root. No Dockerfile
and no custom build pipeline. Never package secrets.

## [Redeploy / update application](#redeploy)

**What:** Ship a new version of an app that already exists.

**Why:** Agent-built apps change constantly. Updating must be as cheap as
deploying, and must not strand the app's data or configuration.

**When:** Any change to an app that is already live.

**How:** Exactly the same call as [Deploy](#deploy), with **the same
`X-App-Name`** and a new `X-App-Version`. There is no separate update
endpoint and no "create then deploy" sequence.

Use the deploy token if the app is claimed — an anonymous deploy cannot
update a claimed app.

**Limitations:** The name is what decides *which* app you update — a new
name silently creates a second app on a second subdomain. Env vars, custom
domains and `DATA_DIR` data all carry over untouched; you do not resend
them. A redeploy schedules a fresh container, so anything written outside
`DATA_DIR` is lost. Each redeploy is a new history entry, so it is safe to
repeat but not free.

## [Static sites](#static-sites)

**What:** An upload that is just files — an `index.html` and its assets, a
`public/` folder, or a `Staticfile` — is published directly. There is no
build and no server process.

**Why:** A plain website doesn't need a server. Publishing the files is
faster and has nothing to crash.

**When:** Detected automatically on every deploy. The reply says so:
`app.kind` is `"static"` and `status` is `"publishing"`. A single-page app
that needs a build step (Vite, Create React App and similar) is still built
and run as a server app.

**How:** Deploy it like any other app. It is usually live within a couple of
seconds; `GET .../status` then reads `live`.

**Limitations:** Because nothing runs on the server:

- **No logs.** `GET .../logs` answers that a static site has no app logs.
- **No env vars.** Setting or applying one is refused with `409`
  `not_supported_for_static`. Put configuration in the files instead.
- **No memory setting**, no `DATA_DIR`, and no scale-to-zero.
- **One way only.** A server app can be redeployed as a static site (its
  server is removed), but a static site can't become a server app:
  that upload is refused with `422` `app_kind_changed`. Use a new app name.

## [Application / project identity](#identity)

**What:** `X-App-Name` is the app's identity — and simultaneously its public
subdomain. There is no separate project id, and no create-a-project step.

**Why:** One identifier an agent can derive and remember, rather than an id
it has to store and look up. It also means the URL is predictable before the
first deploy finishes.

**When:** Every call. Status, logs, env vars, history, rollback and showcase
are all addressed by app name.

**How:** Choose a name matching `^[a-z0-9-]+$`, 3–63 characters, with no
leading or trailing dash. Slugify
anything given in prose: "My Landing Page" → `my-landing-page`. Reuse it
verbatim for every subsequent operation on that app.

**Limitations:** **Unique platform-wide, not per company** — if another
company holds the name you get `409 app_name_taken`, and the only correct
response is to choose a different name. That error does *not* mean "your app
already exists"; redeploying your own app is an ordinary success. Some names
are reserved (`ship`, `api`, `www`, `login`, `docs`, `admin`, `mail`, and
others) — treat a rejection as authoritative. The **slug cannot change**: a
different slug is a different app, on a different URL. The app's *display
name* can be changed with `PATCH /apps/<name>` — see
[Renaming an app](#rename) — but that never moves the URL.

## [Deployment status](#status)

**What:** The outcome of the most recent deploy attempt, plus the app's
current running state.

**Why:** Deploying is asynchronous. Without polling this, an agent cannot
know whether the app it just uploaded actually works.

**When:** After every deploy and every rollback, until it resolves.

**How:**

```bash
curl "https://ship.embarko.ai/apps/my-app/status"
```

The reply's `status` is `building` or `publishing` while it works, then
`live`, `failed` or `crashed`. Each reply also carries `next`, the one thing
to do now: while building, poll again; once live, give the user the URL and
claim the app if it is temporary; once claimed, offer the showcase; on a
failure, read the logs it links to. Poll every 10 seconds (2 for a static
site). Report the live URL only on `live`.

**Limitations:** No token while the app is an unclaimed anonymous deploy;
the owning company's token once claimed — and a wrong token then returns
`404`, never confirming the app exists. The status is held in memory and
reflects the latest attempt only; for durable history use
[deployment history](#history). Give up after about 10 minutes and read the
logs.

## [Build errors](#build-errors)

**What:** The output of a build that failed before the app ever started.

**Why:** A failed build starts no container, so runtime logs don't exist —
without this, a failed deploy would be undiagnosable from outside.

**When:** `status` is `failed` and the app never came up.

**How:** The same logs call. When there are no runtime logs, it returns the
**build** output instead, carrying `source: "build"` and an explanatory
`note`:

```bash
curl "https://ship.embarko.ai/apps/my-app/logs?stream=stderr"
```

The failing command is named there. Read it before changing anything.

**Limitations:** The most common signature is `exit code: 127` — "command
not found" in the build image, meaning the build tool isn't in the app's
dependencies, or the real app is in a subdirectory whose dependencies were
never installed. A trailing `docker-import ... no such file` line is a
cascade, not the cause. Some build failures are rejected *before* the build
runs and surface as `422` codes on the deploy call instead — see
[troubleshoot.md](troubleshoot.md).

## [Runtime errors and logs](#logs)

**What:** The tail of the running app's `stdout` and `stderr`.

**Why:** It is the only window into a live app's behaviour.

**When:** The app is up but wrong, crashing, or restarting.

**How:**

```bash
curl "https://ship.embarko.ai/apps/my-app/logs"
curl "https://ship.embarko.ai/apps/my-app/logs?stream=stderr"
```

Returns `{ available, allocId, stream, logs }`. If nothing has ever
deployed: `{"available": false, "reason": "..."}` with a `next` step. A
[static site](#static-sites) has no logs at all, and the reply says so.

**Limitations:** **A snapshot at call time, not a live stream** — poll to
follow along. No retention guarantee, and always the most recent allocation
whether or not it is healthy. Two signatures mislead: `OOM Killed` /
`Exit Code: 137` is the 256MB limit, and `Not Restarting` /
`Exceeded allowed attempts` is a crash loop whose real cause is logged
*above* it. For durable, long-retention logs, ship them from inside your app
to your own service.

## [Database](#database)

**What:** The app embeds its own database — SQLite via `better-sqlite3` —
and writes the file under `DATA_DIR`, which survives every redeploy.

**Why:** Most agent-built apps need relational storage but not a database
server. Embedding one removes provisioning, connection strings, credentials
and a second moving part.

**When:** The app needs structured data to outlive a deploy or restart —
records, accounts, orders, content.

**How:** Open the database at a path under `DATA_DIR` and create its
directory on startup:

```js
const dir = process.env.DATA_DIR;
fs.mkdirSync(dir, { recursive: true });
const db = new Database(path.join(dir, "app.db"));
```

**Limitations:** **There is no managed database service** — nothing to
provision, no Postgres or MySQL to connect to, and no connection string to
ask the user for. One process means one writer; SQLite is the right shape
here and a client/server database is not. **Not backed up** — see
[Backups and restore](#backups). Never call `window.storage`; it is a Claude
Artifacts sandbox API and is rejected at deploy time with
`422 unsupported_storage_pattern`.

## [Persistent file storage](#file-storage)

**What today:** Files written under `DATA_DIR` persist across redeploys.
That covers user uploads, generated files and caches.

**NOT AVAILABLE YET:** a managed object store — durable file storage
separate from the app's own disk, with its own URLs, redundancy and
lifecycle.

**Why it matters:** `DATA_DIR` is one directory on one machine. It is
persistent, but it is not an object store and is not redundant.

**When:** Any time the app accepts uploads or writes files it must keep.

**How, today:** Write under `path.join(process.env.DATA_DIR, "uploads")`,
creating the directory with `{ recursive: true }` on startup. Serve files
back through your own route.

**Limitations:** Not backed up. Disk is **not quota-enforced**, which is an
obligation rather than headroom — cap upload sizes and evict caches
yourself, because a runaway app affects the shared host. No CDN in front of
it, no signed URLs, no lifecycle rules. Large media is a poor fit.

## [Secrets and app setup](#secrets)

**What:** Per-app environment variables, encrypted at rest and exposed only
to that app's runtime.

**Why:** Secrets must not live in the source — the tarball becomes an image,
and anything in it ships with the app.

**When:** Any API key, credential, or environment-specific setting. Not
for [static sites](#static-sites): they run no process, so env var writes
to them are refused.

**How:** Requires a deploy token. Write, then **apply**:

```bash
curl -X PUT "https://ship.embarko.ai/api/apps/my-app/env-vars/STRIPE_KEY" \
  -H "Authorization: Bearer $DEPLOY_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"value": "sk_live_..."}'

curl -X POST "https://ship.embarko.ai/api/apps/my-app/env-vars/apply" \
  -H "Authorization: Bearer $DEPLOY_TOKEN"
```

`GET /env-vars` lists keys; `PUT /env-vars` replaces all;
`DELETE /env-vars/<key>` removes one.

**Limitations:** **A write alone does not reach the running app** — call
`apply` or redeploy, or the app keeps using the old value. **Values are
write-only**: `GET` returns keys only, so a secret cannot be read back by
you or anyone else holding the token. Keys must match
`^[A-Za-z_][A-Za-z0-9_]*$`. This is not a managed secrets store — no
rotation, no versioning, no sharing between apps.

## [Scheduled jobs](#scheduled-jobs)

**NOT SUPPORTED.** There is no cron, no timer, and no way to have Embarko
invoke your app on a schedule. Don't rely on an in-process scheduler
(`node-cron`, APScheduler, a `setInterval` loop) either: the process restarts
on every redeploy and may be stopped when idle, so the schedule is not
guaranteed to fire.

**Why it matters:** Reports, cleanups, digests and polling all want a
schedule, and an app that quietly assumes one will simply never run that
code.

**When you'd want it:** Anything recurring — a nightly export, an hourly
sync, a weekly email.

**How, today:** Keep the app on Embarko and trigger the schedule from
outside it. Expose an HTTP route that does the work, protect it with a
secret from [env vars](#secrets), and have an external scheduler call it.
Do not try to fake it with an in-process timer: the app can be restarted or
rescheduled at any time, so a `setInterval` is not a schedule.

**Limitations:** Tell the user this is external until it ships. Do not
report a scheduled feature as working because the route exists.

## [Background jobs and workers](#workers)

**NOT AVAILABLE YET.** Planned. There is no worker process, no queue, and no
supported way to run work that outlives the request that started it.

**Why it matters:** Embarko runs **one long-lived process per app**,
listening on `PORT`. Work started in the background competes with request
handling for the same 256MB and the same CPU share, and is lost if the
container is rescheduled.

**When you'd want it:** Image or video processing, long imports, retries
with backoff, anything measured in minutes.

**How, today:** Keep the work inside the request if it is short. If it is
not, run that piece off-platform and have the Embarko app call it and store
the result. See
[when Embarko doesn't fit](overview.md#not-right-when).

**Limitations:** No queue, no retry semantics, no concurrency control, and
no instance count to raise. A job that outlives its request has no guarantee
of finishing.

## [Public HTTP endpoints and webhook routes](#http-endpoints)

**What:** Every path on the app's URL reaches the app. Routing is the app's
own business — including routes that exist to receive webhooks from Stripe,
GitHub, or anything else.

**Why:** It means no route registration, no gateway configuration and no
per-endpoint setup. If the app serves it, it is reachable.

**When:** Any public API, form handler, callback URL or webhook receiver.

**How:** Handle the path inside the app and give the third party
`https://<app-name>.embarko.app/<your-path>`. Verify webhook signatures
yourself, using a secret from [env vars](#secrets) — the platform does not
authenticate inbound requests for you.

**Limitations:** **HTTPS only** — no custom ports, no raw TCP, no private
networking between apps. Response headers, including
`Content-Security-Policy`, are set by the platform at the edge and override
what your app sets. A webhook that expects a fast acknowledgement is at odds
with having [no background workers](#workers) — acknowledge immediately and
keep the work short.

**WebSockets are not supported.** This includes libraries built on them
(Socket.IO, `ws`, Pusher-style realtime). An app that needs live push — chat,
multiplayer, live dashboards — will deploy but its realtime features won't
work. Use plain HTTP requests instead, polling from the browser on an
interval.

**Unconfirmed:** request timeout, maximum request and response body size,
and whether server-sent events are supported. These are not documented; do
not design around a particular value until they are.

## [Default Embarko domain](#default-domain)

**What:** Every app is served at `https://<app-name>.embarko.app` from
its first deploy.

**Why:** The user gets a shareable link immediately, with no domain to buy
and no DNS to configure.

**When:** Always. It is the URL you hand back.

**How:** Nothing to do — it follows from the app name. Choose the name
carefully, because it *is* the subdomain.

**Limitations:** The name rules and reservations in
[Application identity](#identity) apply. The subdomain cannot be changed;
a different name is a different app. It keeps working after a custom domain
is attached.

## [Custom domains](#custom-domains)

**What:** The user's own domain in front of the app, alongside the default
URL.

**Why:** A real product needs a real domain.

**When:** The user asks for it, and owns the domain.

**How:** Agent-callable, apart from the DNS record itself. Register the
domain, hand the returned record to the domain's owner, then verify:

```bash
# 1. Register it — returns the exact DNS record to create.
curl -X POST "https://ship.embarko.ai/apps/my-app/domains" \
  -H "Authorization: Bearer $DEPLOY_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"domain": "app.yourdomain.com"}'

# 2. After the owner creates that record and it propagates:
curl -X POST "https://ship.embarko.ai/apps/my-app/domains/app.yourdomain.com/verify" \
  -H "Authorization: Bearer $DEPLOY_TOKEN"
```

`GET /apps/my-app/domains` lists what's registered;
`DELETE /apps/my-app/domains/<domain>` removes one.

**Limitations:** **You cannot create the DNS record** — only whoever
controls the domain can, at their DNS provider. That is the one step that
goes back to the user, and nothing gets around it. A subdomain gets a
`CNAME`; an apex gets an `A` record, which bypasses any CDN or DDoS proxy
in front of it, so prefer a subdomain. On Cloudflare the record must be
**DNS-only (grey cloud)** — a proxied record never verifies. Verify is safe
to call repeatedly while DNS propagates; routing activates only when it
confirms. Certificate issuance uses an HTTP-01 challenge and needs **port 80
reachable and unredirected**. Removing a domain never affects the default
`*.embarko.app` URL.

## [Automatic HTTPS](#https)

**What:** TLS certificates are issued and renewed automatically, for both
`*.embarko.app` and connected custom domains.

**Why:** No certificate to buy, install, or remember to renew.

**When:** Always on. There is no HTTP-only mode.

**How:** Nothing to do.

**Limitations:** Certificates for a custom domain are only issued once its
DNS verifies, and issuance needs port 80 reachable for the challenge. Data
is encrypted in transit; at rest it is encrypted by the storage provider.

## [Application authentication (end-user login)](#app-auth)

**NOT AVAILABLE YET.** Actively in progress.

**What it will be:** A building block for the **app's own end users** —
signup, login and sessions provided by Embarko, so the agent does not have
to build an auth system for every app.

**What it is not:** [Agent/API authentication](#agent-auth), which is the
deploy token you use to call the platform. Those are different things and
should never be conflated in a message to a user.

**When you'd want it:** Any app with accounts — a CRM, a dashboard, anything
per-user.

**How, today:** Build authentication into the app. Sessions, a users table
in SQLite under `DATA_DIR`, and hashed passwords all work normally here; the
app is a real server. Do not wait for the platform feature, and do not tell
the user one exists.

**Limitations:** Nothing is provided today — no identity provider, no OAuth
integration, no session handling, no user store.

## [Access protection (private apps)](#access-protection)

**NOT AVAILABLE YET.** Planned.

**What it will be:** A gate in front of the **whole app**, so only invited
people can open it at all. Distinct from [end-user login](#app-auth): that
gives an app users, this makes an app private.

**When you'd want it:** An internal tool, a client demo, a staging version
that shouldn't be public.

**How, today:** Every deployed app is **publicly reachable by URL**. If it
must be private, the app has to enforce that itself — a password gate on
every route, for instance. An unguessable app name is not privacy.

**Limitations:** No IP allowlist, no basic-auth toggle, no preview
protection. Tell the user plainly that the URL is public if they assume
otherwise.

## [Deployment history](#history)

**What:** The durable record of every deploy: its id, its version, when it
ran, and whether it succeeded.

**Why:** It is how you know what is running, what changed, and what you can
return to.

**When:** Before a rollback, and whenever the user asks what shipped.

**How:**

```bash
curl "https://ship.embarko.ai/api/apps/my-app/deployments" \
  -H "Authorization: Bearer $DEPLOY_TOKEN"
```

Newest first. `GET /deployments/<id>` returns one entry, which is also how
you poll a rollback.

**Limitations:** Requires a deploy token. It is a record, not an archive —
the **build images** behind old entries are pruned, so an entry can exist
that you can no longer roll back to. Pass a meaningful `X-App-Version` or
entries are just timestamps, and never reuse a tag for different code.

## [Rollback](#rollback)

**What:** Put an earlier successful build back in service — a pointer flip
onto an image that already exists, with no rebuild.

**Why:** It makes letting an agent ship often a safe thing to do. Recovery
is seconds, not another build.

**When:** A deploy broke something and the previous version was fine.
Restore first, debug afterwards.

**How:** Two steps — the deployment id in the URL is what chooses the
version:

```bash
curl "https://ship.embarko.ai/api/apps/my-app/deployments" \
  -H "Authorization: Bearer $DEPLOY_TOKEN"

curl -X POST \
  "https://ship.embarko.ai/api/apps/my-app/deployments/<deploymentId>/rollback" \
  -H "Authorization: Bearer $DEPLOY_TOKEN"
```

Answers `202`; poll the returned deployment until it leaves `in_progress`.

**Limitations:** Requires a deploy token. Only **successful** deployments
with a recorded image are valid targets — pick the newest good one *before*
the bad deploy, not simply the previous entry. Runs the old image under
**current** configuration: today's env vars and domains, not the originals.
Only the last few images are kept; a pruned target returns
`422 rollback_image_unavailable`, whose `retainCount` says how far back you
can reach. History is not rewritten — a rollback lands as a new entry. It
does **not** restore data: `DATA_DIR` is untouched.

## [Backups and restore](#backups)

**NOT AVAILABLE YET.** Actively in progress.

**What it will be:** Automatic backups of an app's persistent data, with a
restore path.

**What exists today:** Nothing. Data under `DATA_DIR` survives redeploys and
restarts, and that is the whole guarantee. There is **no snapshot, no
backup, and no restore** — it is durable against your deploys, not against
hardware loss.

**When you'd want it:** Any app holding data the user would be upset to
lose. Which is most of them.

**How, today:** Have the app export its own data — a scheduled dump the user
can download, an endpoint that streams the SQLite file, or a copy pushed to
storage they control. Tell the user this is the situation rather than
letting them assume backups exist.

**Limitations:** [Rollback](#rollback) is not a backup — it restores code,
never data. Deleting an app destroys its data irreversibly.

## [Application health](#health)

**What:** The `health` object in the status response, describing the app's
current running state independently of the last deploy's outcome.

**Why:** A deploy's result and an app's condition are different facts — an
app can be healthy while the newest deploy failed, because the previous
version is still serving.

**When:** Checking whether a live app is actually up, or after a deploy that
succeeded but behaves wrongly.

**How:**

```bash
curl "https://ship.embarko.ai/apps/my-app/status"    # read the `health` field
```

**Limitations:** **There is no separate health endpoint, no uptime
monitoring, no alerting, and no notification when an app goes down.** You
learn about a problem by looking. The platform restarts a crashed app a
limited number of times and then stops, logging
`Not Restarting` / `Exceeded allowed attempts`. If the user needs to know
about downtime, they need external monitoring pointed at their URL.

**Unconfirmed:** the exact fields inside `health`, and whether a
readiness/liveness check can be configured per app. Branch only on the
status reply's `status` field (`live`, `crashed`, …), which is specified.

## [Application isolation and security](#isolation)

**What:** Each app runs in its own environment, with its own filesystem and
its own volume, on managed infrastructure certified to ISO/IEC 27001.

**Why:** It is the answer to "where does my data live and who else can reach
it" — a question that decides whether an app can hold anyone else's data.

**When:** The user asks about security, data residency, or compliance.

**How:** Nothing to configure. For a compliance answer, point at the
[DPA](/dpa) and [Privacy Policy](/privacy) rather than summarising them.

**Limitations:** The ISO/IEC 27001 certificate belongs to the
**infrastructure provider**, covering their facilities and their security
management — it is **not** a certification of Embarko, and "Embarko is ISO
27001 certified" is false. It does not cover `embarko.ai` or the dashboard,
which run elsewhere. **Do not tell a user which country their app or data is
in**: region selection is not available, the region is not guaranteed, and
the platform makes no data-residency commitment outside the [DPA](/dpa). **Container-to-container network isolation is
unverified** — do not treat it as a security boundary; authenticate and
encrypt anything sensitive. Filesystem and storage isolation are real.

## [Resource and runtime defaults](#resources)

**What:** What every app gets without asking: 256MB of memory, a shared CPU
allocation, one process, and a runtime auto-detected from the source by
[Railpack](https://railpack.com).

**Why:** There is nothing to size, select or provision. The defaults are the
contract, which is why an agent never needs to ask a user about them.

**When:** Designing the app, and diagnosing an OOM.

**How:** Build to the defaults. Read `process.env.PORT`, bind `0.0.0.0`,
ship no Dockerfile, use a **production** start command, and keep a
conventional project layout so detection works.

**Limitations:** **Memory is 256MB and hard-enforced** — over it is an OOM
kill (exit code 137), not throttling, and there is **no self-serve way to
raise it**: no agent call, and the dashboard control has been removed. CPU
is a relative share, not a reservation, so a busy neighbour can slow you
down — add timeouts around CPU-bound work. No GPUs. No Dockerfile or custom
build step; Railpack supports some runtime-serving overrides (a `Caddyfile`
for static sites) but not replacing the build. Disk is not quota-enforced,
which is an obligation, not headroom.

## [Delete application](#delete)

**What:** Tear down the running app, its routing, its image and its record.

**Why:** Apps are cheap to create, so they accumulate. Removing one should
be deliberate.

**When:** The user explicitly asks to remove an app permanently.

**How:** Agent-callable, but the token alone is not enough — you must
resend the app's own name to confirm:

```bash
curl -X DELETE "https://ship.embarko.ai/apps/my-app" \
  -H "Authorization: Bearer $DEPLOY_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"confirmAppName": "my-app"}'
```

Omitting `confirmAppName`, or getting it wrong, returns
`400 confirmation_required` and deletes nothing.

**Limitations:** **Irreversible, and there is no backup to restore from** —
the app's `DATA_DIR` data is destroyed with it, and the name is released for
anyone to take. **Always show the user exactly what you are about to delete
and get their go-ahead first.** The `confirmAppName` field guards against a
misread instruction, not against an agent that is confident and wrong — see
[When to involve the human](escalation.md#destructive).

## [Renaming an app](#rename)

**What:** Change an app's **display name** — what the dashboard shows. The
slug, and therefore the live URL, never changes.

**Why:** An app slugged `my-app` in a hurry can still be presented as
"Customer Portal" without redeploying or moving its URL.

**When:** The user dislikes the displayed name, or it was auto-derived.

**How:**

```bash
curl -X PATCH "https://ship.embarko.ai/apps/my-app" \
  -H "Authorization: Bearer $DEPLOY_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"name": "My App"}'
```

**Limitations:** Display name only. **The URL does not move** — if the user
wants a different address, that is a new deploy under a new name (and a
different app), or a [custom domain](#custom-domains). Keep addressing every
other call by the original slug.

## [MCP connector](#mcp-connector)

**What:** An Embarko MCP connector, so an agent can deploy through its
tool interface instead of making HTTP calls itself. It appears in the
connector list as **Embarko**.

**Why:** Two reasons. It needs no `curl`, no packaging and no token — the
connector carries the account from the user's login session. And its
requests come from the connector infrastructure rather than your own
environment, so it works where a sandboxed agent cannot reach
`ship.embarko.ai` at all.

**When:** Whenever it is available — it is the shorter path. And
specifically when a direct call is being blocked before it leaves your
environment; see
[If you can't reach the API at all](agent-playbook.md#no-connectivity).

**How:** The user connects it in their AI tool's connector settings; you
cannot install it for them. Once connected it exposes:

| Tool | What it does |
| --- | --- |
| `Embarko Onboarding` | Returns the deploy instructions. Read it first |
| `Deploy App` | Deploys, given an app `name` and a `source_url` |
| `Submit Feedback` | Reports a problem with Embarko itself |

**Limitations:** The big one — **`source_url` must be a direct link to a
`.tar.gz` that is publicly fetchable**, with no login wall and no redirect.
The connector does not upload a local folder the way `POST /apps` does, so
the source has to be hosted somewhere reachable first. If it isn't, use the
HTTP API instead.

**There is no status or logs tool.** The connector can start a deploy but
cannot tell you whether it finished, and cannot show you why it failed. A
deploy is not done when the tool call returns. Where you have network
access, poll [status](#status) over HTTP; where you don't, say plainly that
you cannot confirm it yet rather than reporting success.

The same runtime rules apply to a connector deploy as to any other: `PORT`
and `0.0.0.0`, no Dockerfile, `DATA_DIR` for anything durable, 256MB, and a
deploy with no account connected is deleted after 24 hours.

## [Agent / API authentication](#agent-auth)

**What:** How *you* authenticate to Embarko: a company-wide deploy token,
`Authorization: Bearer <token>`. Distinct from
[end-user login](#app-auth) for the app itself.

**Why:** It is deliberately minimal — one credential, obtainable without a
browser, so an agent is never blocked on a signup flow.

**When:** Claiming an app, and every control-plane call: env vars, history,
rollback, showcase. **Not** needed for a first deploy.

**How:** Check `$DEPLOY_TOKEN` and `~/.embarko/credentials` before asking
for anything. If neither exists, request one by email:

```bash
curl -X POST "https://ship.embarko.ai/api/public/deploy-tokens/request" \
  -H "Content-Type: application/json" -d '{"email": "them@example.com"}'
```

Save a new token to `~/.embarko/credentials` (`chmod 600`).

**Limitations:** Always returns `202`, whether or not the address exists or
you hit a limit. **The token is emailed to the user and never returned to
you** — ask them to paste it. Rate limited to 5/hour per email and 10/hour
per IP; since the response is identical either way, call it once and never
loop. Tokens are shown once and hashed at rest — a lost one can only be
rotated, not recovered (the old one works for one hour). They authenticate a
*company*, not a person, deploy only, and do not sign in to the dashboard. A
present-but-invalid token is always a hard `401`, never treated as
anonymous.

## [Account and project limits](#limits)

**What:** How many apps a company can run at once, and what usage is
included, are set by its plan.

**Why:** An agent should know a deploy can be refused for reasons that have
nothing to do with the app's code.

**When:** Before deploying many apps for one user, or if a deploy is
rejected for a reason the [error table](api.md#deploy) doesn't explain.

**How:** Plans and their limits are published at
[embarko.ai/pricing](/pricing), and change independently of this page.
Anything plan-related — upgrading, paying, changing a limit — is the user's
decision and needs their approval.

**Limitations:** There is no agent-facing endpoint for a company's plan or
remaining quota — [analytics](#analytics) reports one app's traffic, not the
account's limits. Public unauthenticated endpoints have their own
separate limits: token requests 5/hour per email and 10/hour per IP;
anonymous feedback 10/email, 20/IP and 500/hour globally.

## [Also available](#also)

Useful, but outside the core lifecycle above.

### [Anonymous deploys and claiming](#anonymous)

**What:** A deploy with no credential, producing a real live app that can be
claimed later. **Why:** It removes signup from the first deploy entirely.
**When:** Every first deploy, unless you already hold a token. **How:** Omit
`Authorization`; claim by redeploying the same name with a token.
**Limitations:** **Deleted 24 hours after creation.** No reminder email — the
only warnings are `app.expiresAt` with the claim steps in the `next` field of
the status reply once the app is live, and a countdown banner injected into
HTML pages (a JSON-only API has nothing to inject
into).

### [Showcase listing](#showcase)

**What:** List a deployed app on a Showcase page — the company's own page,
which exists from signup, or an event page (a hackathon or demo day) that
anyone can add to. **When:** The user wants it shown publicly. **How:**
`PUT /api/apps/<name>/showcase` with `collectionSlug`, `name`, `tagline`,
`creatorName`. `collectionSlug` is the page's slug from its URL
(`/showcase/<slug>`). **Limitations:** Deploy token required; calling again
updates rather than errors; `404 SHOWCASE_COLLECTION_UNKNOWN` for an unknown
slug, `403 SHOWCASE_COLLECTION_PRIVATE` for another company's page.

### [Sending feedback as an agent](#feedback)

**What:** Report a platform limitation or a misleading doc from inside a
deploy. **When:** Something blocked you — that is more useful reported than
worked around. **How:** `POST /apps/<name>/customer-query` with an
`X-Agent-Name` header and `{type, message}`. **Limitations:** `X-Agent-Name`
required; `type` exactly `feature`/`feedback`/`other`; `message` 1–5000
characters.

### [Analytics](#analytics)

**What:** Request traffic (total and by status code) and CPU/memory usage.
**When:** The user asks how the app is doing, or you are diagnosing load.
**How:** `GET /apps/<name>/analytics?range=7d` with a deploy token — `range`
is `24h`, `7d`, `30d`, `90d` or `all` (default `24h`). The same data is on
the dashboard's **Analytics** tab. **Limitations:** Returns `503` if the
analytics subsystem is unreachable — that is not zero traffic, so do not
report it as such. No alerting and no metrics export.
